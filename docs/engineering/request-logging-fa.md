# لاگ درخواست‌های MalGuard AI — آمادهٔ بازبینی

وضعیت: **IMPLEMENTED — NOT LIVE VERIFIED**. هیچ تغییر Production یا ظاهر سایت در این مرحله انجام نشده است.

برای هر درخواست، سرور شناسهٔ UUID تازه می‌سازد و آن را در `X-Request-ID` پاسخ قرار می‌دهد. شناسهٔ فرستاده‌شده توسط کاربر جایگزین آن نمی‌شود. درخواست‌های ردشده، خطای JSON، محدودیت نرخ، قطع ارتباط و پاسخ عادی هم ثبت می‌شوند. هر درخواست فقط یک رخداد پایان دارد؛ خرابی خروجی لاگ نباید نتیجهٔ دوم به جریان چت اضافه کند یا کنترل‌های مجوز/نرخ را خاموش کند.

فیلدها: شناسهٔ رخداد، درخواست و هم‌بستگی، زمان، شدت، سرویس، محیط، نسخه، مسیر ثابت، کد HTTP، کد خطای مجاز، ارائه‌دهنده/مدل مجاز، مدت، شمار تلاش و وضعیت رسیدگی دستی. شدت‌های DEBUG/INFO/WARN/ERROR/CRITICAL فقط مقادیر ازپیش‌مشخص‌اند؛ رخدادهای HTTP معمولاً از INFO/WARN/ERROR استفاده می‌کنند. نام مدل/ارائه‌دهنده از فهرست ثابت انتخاب می‌شود؛ شناسهٔ دلخواه یا متن کاربر لاگ نمی‌شود.

محتوای پیام، فایل، URL، هدر، ایمیل، نام حساب، رمز، توکن و متن خام خطای ارائه‌دهنده، فیلد مجاز لاگ نیستند. مسیرهای ناشناخته نیز به `unmatched` تبدیل می‌شوند. نسخه و Deployment فقط قالب معتبر فیلدهای شناخته‌شدهٔ محیط استقرار را قبول می‌کنند.

## ظرفیت، نگهداری و حدود واقعی

- حافظهٔ پیش‌فرض: ۲۵۰ رخداد، حداکثر یک ساعت؛ با پایان اجرای سرور از بین می‌رود. سقف تنظیم‌شدنیِ کد ۱۰۰۰ رخداد و ۲۴ ساعت است.
- خروجی JSON پیش‌فرض: حداکثر ۳۰۰ رخداد در دقیقه برای هر اجرای سرور. رخدادهای مازاد شمارش می‌شوند؛ این شمارنده لاگ اضافی بی‌نهایت تولید نمی‌کند.
- حداکثر پنج نوشتن ناهم‌زمان می‌تواند در انتظار بماند؛ خروجی‌های مازاد حذف و شمارش می‌شوند.
- خرابی sink در شمارندهٔ `sinkFailures` مشخص می‌شود؛ متن خطای sink منتشر نمی‌شود.
- این حافظه نه پایگاه دادهٔ مشترک است و نه جای سهمیه/کنترل هزینهٔ سراسری. محدودیت نگهداری و مجوزهای خود Vercel/GitHub در این تغییر بررسی یا تغییر نکرده‌اند. نمی‌توان از TTL محلی، حذف لاگ ابری را نتیجه گرفت.
- حافظهٔ لاگ از HTTP عمومی قابل خواندن نیست. داشبورد خصوصی و کنترل دسترسی مدیریتی هنوز در این PR ساخته نشده‌اند.
- Correlation ID فعلاً در همین API برابر Request ID است؛ اتصال مشترک با دروازهٔ مدل و رابط کاربری هنوز پیاده نشده و «ردگیری انتها‌به‌انتها» ادعا نمی‌شود.
- `retryCount: 0` یعنی این API تلاش مجددی انجام نداده است؛ این مقدار شمار تلاش‌های داخلی ارائه‌دهندگان دیگر نیست. `manual_review` یعنی موتور تعمیر خودکار به این رخداد متصل نیست.

## آموزش پیدا‌کردن خطا

1. در مرورگر، بخش Network را باز کنید و درخواست `/api/malguard-ai/chat` را انتخاب کنید.
2. از Response Headers فقط `X-Request-ID` را کپی کنید. بدنهٔ درخواست، هدر Authorization و محتوای چت را کپی نکنید.
3. در Vercel، پروژهٔ API و Deployment مرتبط را باز کنید؛ در Logs همین شناسه را جست‌وجو کنید. دسترسی واقعی داشبورد و مدت نگهداری به حساب مالک بستگی دارد.
4. `statusCode`، `errorCode` و `durationMs` را بررسی کنید: 429 نشانهٔ محدودیت درخواست، 503 مشغول/غیرفعال‌بودن سرویس و 500 خطای برنامه است. خطای یک مدل ممکن است داخل پاسخ HTTP 200 قرار داشته باشد؛ در آن حالت `errorCode` و شدت رخداد هم مهم‌اند.
5. با دادهٔ مصنوعی همان مسیر را در محیط آزمایشی بازتولید کنید. شناسه، نسخه و مسیر ثابت برای گزارش کافی‌اند؛ پیام و فایل خصوصی لازم نیست.

این راهنما جای داشبورد کامل MalGuard Debug Center، نسخهٔ امن قابل کپی، سیستم هشدار، نگهداری مشترک و دو موتور تعمیر را نمی‌گیرد؛ آن‌ها مراحل باقی‌مانده هستند.
